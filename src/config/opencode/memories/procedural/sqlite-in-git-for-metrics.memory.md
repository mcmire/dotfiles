## When to use this
Migrating a small (<~20 MB), structured, **incrementally-appended, single-writer** dataset from a JSON file to a SQLite database committed to Git. Sweet spot: a nightly/periodic ETL-style collection job (e.g. `collect-metrics`). Wrong choice if the data is large, frequently/concurrently written, or sensitive.

## Why SQLite-in-git
- Real constraints (`PRIMARY KEY`, `NOT NULL`, `FOREIGN KEY`, `CHECK`) enforced at write time instead of trusting a JSON blob.
- Zero infrastructure; every commit is a full snapshot (real reversibility via `git revert`).
- Schema, data, and code stay in lockstep in one commit.

## Critical gotcha: store the file UNCOMPRESSED
Git's delta compression works well on SQLite's 4 KB page format — a small change rewrites only a few pages, so nightly deltas are tiny (~KBs against a multi-MB file). Compressing (`.gz`) **defeats** this: any change reshuffles the whole stream, so Git stores a near-full copy every commit. Counterintuitively, the larger on-disk raw file yields far smaller Git history growth. (Refs: keith-trnka.com "SQLite in Git", garrit.xyz "Tracking SQLite Database Changes in Git", HN 38110286.)

## Readable diffs
`.gitattributes`: `data/metrics.sqlite3 binary linguist-generated diff=sqlite3`
`postinstall` (or `~/.gitconfig`):
```
git config diff.sqlite3.binary true
git config diff.sqlite3.textconv 'echo .dump | sqlite3'
```
Requires the `sqlite3` CLI on `PATH` for anyone running `git diff`. Document this as a prerequisite. Verify with `git diff` showing `INSERT INTO ...` lines instead of "Binary files differ".

## Browser dashboards can't read SQLite directly
A static Vite/React SPA `import`s JSON as an ESM module in the browser — it cannot `import` a `.sqlite3`, and there's no runtime server. **Bridge with a generated, git-ignored JSON file:**
- Add an `export-metrics` script + shared `writeGeneratedMetrics(db)` that reads the DB into the exact dataset shape the dashboard already parses (run rows through the existing `parseMetricsData` so shape/coercion is identical).
- Keep it in sync automatically so it's **never** regenerated by hand: append the export to the end of `collect-metrics`, plus `predev`/`prebuild` scripts, plus `postinstall` (the committed DB exists on fresh clone, so `tsc`/build/tests find the file).
- Git-ignore `data/metrics.generated.json`; commit only the `.sqlite3`.
- Vite SSG/SSR is an alternative but adds an entry-server/client split + hydration data-plumbing for no extra benefit over the JSON bridge when goals are constraints/incremental-writes.

## Incremental collection with SQLite
- Replace an in-memory merge with `INSERT OR REPLACE`/`ON CONFLICT(id) DO UPDATE` upserts, writing each table as it's fetched.
- Replace "newest seen" scans with `SELECT MAX(occurredAt) FROM <table> WHERE repository = ?` (optionally an extra predicate, e.g. `AND isRelease = 1`).
- Dates: store as **ISO-8601 TEXT** (keeps `.dump` diffs readable and sortable). Booleans → `INTEGER` 0/1 with a `CHECK`.
- Replace a scalar `updatedAt` with a `collectionSessions` log table (`startedAt`, `repositories` JSON, `tables` JSON); derive "collected at" from `MAX(startedAt)`.

## "Free mutex" — caveat
`better-sqlite3` is synchronous/single-connection, so concurrent in-process tasks (e.g. Listr `concurrent: true`) serialize writes safely. It is **NOT** a cross-process lock — two simultaneous runs can hit `SQLITE_BUSY`. Fine for a single nightly job; don't rely on it as a general mutex.

## Practical notes (Yarn 4 / LavaMoat / Vitest)
- `better-sqlite3` ships prebuilt binaries via `prebuild-install`, so **no LavaMoat `allowScripts` entry is needed** — confirm with `yarn allow-scripts auto` ("configuration looks good").
- better-sqlite3 `.all()`/`.get()` return `unknown` → a justified `as {...}` assertion at query sites is unavoidable.
- Correlating a generic `table` name with a per-table converter union defeats TS inference; a single justified assertion `ROW_TO_COLUMNS[table] as (row: MetricsData[Name][number]) => ColumnValues` (guarded by `satisfies` on the map) is the pragmatic fix.
- Test DB code against `:memory:` databases; extract the orchestrator (e.g. `collectMetrics({ client, database, ... })`) so it's Nock-testable.
- Octokit `paginate` on the actions-runs endpoint needs `total_count` in the mocked reply or it returns the envelope object (yielding invalid dates downstream).
- `exactOptionalPropertyTypes`: don't pass `where: undefined`; spread conditionally (`...(where === undefined ? {} : { where })`).

## CI (GitHub Actions)
If jobs accumulate data across a sequential matrix via an artifact, just swap `data/metrics.json` → `data/metrics.sqlite3` — each job downloads the prior DB and upserts. Update deploy/commit/PR workflows to pass/commit/publish the `.sqlite3`.

## Bonus payoff
Migrating real JSON via the DB primary key surfaced 31 exact-duplicate rows collapsed losslessly — the constraint approach immediately caught latent data-integrity issues.
